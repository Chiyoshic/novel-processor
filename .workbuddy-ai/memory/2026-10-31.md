## 小说库采集层：多站点架构 + syosetu 解析器

**目标**：把不同小说站点的作品归一化为统一 JSON，供后续整理/检索/导出。

**架构决策**
- 分层：Adapter（站点知识）→ Pipeline（站点无关编排）→ 领域模型 → 消费层。流水线内禁止出现站点特有逻辑。
- 适配器契约 `SiteAdapter`（`src/lib/types.ts`）：`match / resolve / indexUrl / episodeUrl / parseIndexPage / parseEpisodePage / fetchMeta` + `capabilities` 能力声明。
- 目录页解析返回「有序条目流」`IndexItem[]`（chapter | episode 混排），归章由流水线 `assembleStructure()` 在所有分页合并后统一完成 —— 解决「章跨页」切断问题。
- 双源策略：HTML 负责章/话/URL/时间；官方 API（api.syosetu.com/novelapi）负责完结状态、字数、总话数、标签、分级。富化失败降级不阻断。
- 选择器集中在 `sites/<site>/selectors.ts`，改版只改一个文件。

**关键实现细节（踩过的坑）**
- syosetu `end` 字段实测语义：`1 = 連載中`，`0 = 已完结（含短編）`；短編与完结连载靠 `novel_type`（1 連載 / 2 短編）区分。非官方文档字面语义，已在 `api.ts` 注释标注。
- 目录页只有「最終エピソード掲載日」的日精度；秒级时间只能来自 API。
- 时间必须补 `+09:00` 偏移，否则下游按 UTC 解析会偏 9 小时。
- 文本归一化必须**保留 U+3000 全角空格**（日文标题/人名分词、段首缩进），只清洗 ASCII 空白 —— 否则「陽七　葵」会变成「陽七 葵」。
- 目录页每页 100 话，分页靠 `.c-pager__item--last` 的 `?p=N`；无分页控件时用单页上限兜底判定。
- 章节正文用 `.p-novel__text`（需排除 `--preface` / `--afterword`），逐 `<p>` 拼接，`<p><br /></p>` 为空行。

**产出**
- `src/lib/{types,errors,time,text,http,pipeline}.ts` + `src/lib/sites/{registry,syosetu/*}`
- `scripts/fetch-novel.ts`（CLI，`npm run fetch -- <id|url>`，支持 `--episode` / `--no-enrich` / `--max-pages`）
- `docs/architecture.md`（含新增站点 checklist、演进路线、已知限制）
- 实测：n4703ix → 159 话 / 8 章 / 387,175 字，完结 2024-09-13，零告警；n9669bk（3 页 286 话）与 n3289ds（连载中 + 截断告警）均验证通过。

**技术栈约定**
- 采集内核放 `src/lib/`（与 Vue 无关，`HttpClient` 为接口，Node/浏览器通用）；cheerio 在 app tsconfig 下类型检查通过。
- tsconfig 开启了 `erasableSyntaxOnly`（禁 enum / 参数属性）与 `noUnusedLocals`。
- 依赖新增：`cheerio`（deps）、`tsx`（devDeps）。

**下一步**：P2 本地书库索引（`data/index.json`）→ P3 增量更新 → P5 跨站去重。

## 追加：批量正文提取（同日）

**背景**：初版只有目录全量 + 正文单话按需，用户确认后补齐批量能力。

**实现**
- `NovelFetcher.fetchEpisodes()`：串行（HttpClient 已是全局串行限速队列，并发无收益且放大风控）；单话失败不中断整批，收集到 `failed[]`；`shouldSkip` 支持断点续传；`onEpisode` 每话即时回调落盘。
- 抽出私有 `fetchOne()` 供单话/批量共用，避免逻辑分叉。
- CLI 新增 `--all` / `--range 1-20` / `--range 1-5,10,20-25` / `--overwrite`；`parseIndexSpec` 支持区间+枚举混合。
- `_manifest.json` 记录 `have`（目录内已落盘数）+ `lastRun`（本次 fetched/skipped/failed/duration）。

**实测**
- `--range 1-3` → 2 新抓 1 跳过（续传生效）；`--range 78-79` → 1 新抓 1 跳过。
- `--all` 跑到第 77 话被用户中止：77 个文件全部有效（无空正文、无序号错位、区间无缺口），1.5MB。
- 结论：中断安全，重跑同命令即自动补齐。

**设计取舍**：正文按话拆文件而非整本大 JSON —— 断点续传粒度即文件、可并行增量处理、单文件损坏只影响一话。

**待办**：`_manifest.json` 仅在正常结束时写入，进程被 kill 时不落盘（续传不依赖它，靠文件存在性判断，可接受）。

## 追加：可配置并发（同日）

**关键认知**：并发与节奏是**两个独立约束**，必须分开建模。
吞吐上限 = `min(concurrency / 平均延迟, 1 / minIntervalMs)`。
只提并发不放宽节奏，吞吐不变（仍被 1/minInterval 封顶）——这是「设了并发却没变快」的根因。

**实现**
- 新增 `src/lib/concurrency.ts`：`mapLimit`（保序并发映射，任一项抛错即停止派发）与 `forEachLimit`（限额遍历，单项失败不互相影响）。
- 重写 `FetchHttpClient` 调度：信号量（**名额转交式** release，避免唤醒与归还竞态）+ `pace()`（**先同步占时间槽再 await**，防止多并发重复分配同一时间槽）。
- 流水线：目录页并发抓取后按页序合并（`mapLimit` 按下标写回，天然保序，否则章会错位）；正文批量改 `forEachLimit`（无序，按话落盘）。
- CLI：`-c/--concurrency`、`--interval`；未显式给 interval 时按 `max(150, 800/n)` 自动推导。
- 两处并发数必须一致，否则任务在流水线并发、在 IO 层排队，表现为「没变快」。

**实测（20 话）**
- c=1（800ms）28.4s → c=4（200ms）6.6s（4.3×）→ c=8（150ms 下限）5.7s（5.0×，收益递减）。
- 结论：**4 并发性价比最高**，8 并发站点侧排队成为瓶颈且更易风控。
- 数据校验：99 个正文文件与目录标题逐一比对，无错位、无空正文、无串号；目录并发抓取后 286 话顺序完整、25 章无告警。
